Why ONNX, and why not the others

HAI runs its speech models on the user's own machine, in the browser, with no Python and no native install. Three of its models are ONNX files run by ONNX Runtime Web. This page says why that fits, what it costs, and what the alternatives would have meant here. Every number is from this repository's own measurements unless a source is named.

The short answer. The constraints are: nothing leaves the machine, it works offline after install, it runs in a browser tab and in the desktop app alike, and it must not need a native binary that Windows may refuse to run. ONNX Runtime Web is the one runtime that runs all three speech models under those constraints, on WebAssembly everywhere and on WebGPU where that is faster, from one file format that the library the app already uses (transformers.js) loads directly.

The honest part. ONNX is a file format, not a speed. What decided the speed was the backend and the precision (a 10 times difference in this project, below), and one of the models is a community export, not an official one.

The tracking models are not ONNX: MediaPipe publishes them as TFLite and its runtime is a separate WebAssembly build. They stay as published. The runtime for the three ONNX models is one pair of files (ort-wasm-simd-threaded, about 14 MB plus a 27 MB variant for WebGPU) shared by all of them.

Why it fits

It runs where the app runs

In a browser tab, in the Electron desktop app and in the end-to-end tests, with the same files. No Python environment to install, no model server to start, no port to open.

Nothing leaves the machine

The model files are served by the app itself from a pinned revision, each checked by SHA-256. An automated test fails if any request or bridge message carries audio.

No fresh native binary

On the reference Windows laptop, Smart App Control refuses new unsigned native binaries: it blocks OpenCascade's Python wheel and Playwright's own Chromium here. WebAssembly runs inside the browser's sandbox and is not a new executable, so it is not blocked.

One loader for three models

transformers.js, already in the app, loads Moonshine and Kokoro from ONNX and runs them on ONNX Runtime Web. Silero VAD uses the same runtime. One runtime, one cache of wasm files, one place to upgrade.

Quantised files exist

int8 files cut Moonshine to a quarter of its fp32 size (74.9 + 90.8 MB against about 540 MB) with identical transcripts in the export's own check. A download of the size users accept.

Permissive licences

ONNX Runtime Web is MIT. The three models are MIT or Apache-2.0. pnpm licenses:check rejects anything GPL, AGPL or non-commercial, and this stack passes it.

What was measured: the backend decides, not the format

Same Moonshine files, same laptop (Intel Arc 140T, 16 cores), same sentence, in Edge. Only the backend changes.

Moonshine base, WebAssembly int80.2 s
Moonshine base, WebGPU int82.0 s

WebGPU has to unpack int8 weights on every run, so the same ONNX file is ten times slower there. It is the other way round for Kokoro: the int8 file on WebAssembly took 2.8 to 3.0 s for 2.4 s of speech (slower than real time), and the fp32 file on WebGPU took 1.1 s. The fp16 file was fast and spoke silence (half-precision overflow). Source: docs/decisions.md, "On-device speech" and "Mochi's voice".

The alternatives, and why not here

OptionWhat it is good atWhy not for these models, here
PyTorch or safetensors, run in PythonThe original format of nearly every model; the newest architectures land here first.Needs a Python environment with PyTorch (hundreds of MB, native wheels) and a process to run it in, with the audio sent across to it. That is the install, the port and the native-binary risk the app avoids. It also cannot run in a browser tab.
TFLite / LiteRTSmall, fast on phones, and what MediaPipe uses: the tracking models here are TFLite.The speech models used here are not published for it, so choosing it means converting and verifying each one ourselves. It stays where the models already are (tracking).
GGUF with llama.cpp or whisper.cppThe format for language models on a laptop; strong quantisation options; Whisper has a well-known C++ port.Each model family would come with its own runtime and its own WebAssembly build (Moonshine, Kokoro and Silero are not in it). Worth a look for a language model if one is ever added as a fallback for commands, not for these three.
WebGPU-only stacks (WebLLM, MLC)Fast language-model inference in the browser.Built for language models, and they need WebGPU. Many of the machines the app targets (and every CI runner) draw in software, so WebAssembly has to work.
Native runtimes (Core ML, DirectML, CUDA, native ONNX Runtime)Use the machine's accelerator fully.One build per platform, a signed native binary to ship, and on Windows with Smart App Control a fresh unsigned binary may simply not run. The browser's WebAssembly sidesteps all three.
A cloud speech or language serviceHighest accuracy for the least local work.Breaks the rule that camera, microphone and model never leave the machine. The browser's own speech service is offered as an opt-in setting for people who choose it, and is off by default.
The browser's built-in speech recognitionNo download at all.It sends audio to the browser vendor (Google for Chrome, Microsoft for Edge), needs a network, and differs between browsers.

What ONNX costs, and what is still a risk

  • ExportMoonshine v2 has no official ONNX export. The one used is a community conversion of the small model (MIT, int8, pinned by revision and hash). transformers.js 4.3.1 does not yet have the model type, so the export declares the older Moonshine type and the audio is padded to whole 5 ms frames. When an official export or library support appears, the lock file should move to it.
  • PrecisionQuantisation is per model and backend: int8 is right on WebAssembly and slow on WebGPU, fp16 broke Kokoro. Each choice here was measured, not assumed.
  • SizeThe WebAssembly runtime is about 14 MB (41 MB with the WebGPU build) before any model, and the voice models together are 496 MB, downloaded once on first run.
  • No streamingThe ONNX export transcribes a whole utterance after speech ends (about 0.3 s). The model is built for streaming; the export and library do not use that yet.
  • Not a lock-inThe app asks a transcriber for text and a speaker for audio; the models sit behind two small workers. Swapping the model or the runtime changes those files and the asset lock, not the app.

When to reconsider

  • An official Moonshine ONNX export, or transformers.js support for its streaming type: move to it and drop the community file.
  • A language model for commands the grammar cannot read: weigh GGUF against ONNX then, on the same 136 spoken phrases and the 630-phrase set in test-assets/commands, for latency in the browser, size and exact-command rate.
  • WebGPU becoming dependable on the machines in use: the int8 and fp16 results above are worth repeating.
