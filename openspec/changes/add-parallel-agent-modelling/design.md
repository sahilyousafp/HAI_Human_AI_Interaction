# Design

## Context

What the code does today (from reading it, with the places that matter):

- **One writer by one line.** `Team.schedule` skips a queued writer while any active task's agent has `writes` (`team.ts:534`). Docs, spec and tests assert it.
- **One undo slot.** `SceneStore.group` is a single field and `Team.groupOwner` a single string. `applyInGroup` merges any edit into whichever group is open and labels it with that group's label, so two concurrent writers would be mixed into one undo step with the wrong label.
- **Identity reaches the right place and stops there.** `createSceneMcpServer(deps, caller)` knows `caller.agent`, but `create_elements`, `update_elements` and `delete_elements` call `deps.apply(ops)` with no agent. `scene.patch` carries a label but no author. Elements are strict objects with no tag or owner field; only free-form `properties` exists. `Rhino` objects already have `hai.*` user strings surfaced as `tags`, and `hai.owner` is advice in a tool description with no code reading it.
- **Ids.** Any string of 1-64 characters. A create with an existing id fails the whole batch (`ops.ts:32`). The importer makes `imp-<random asset>-<i>`, ignores Rhino GUIDs and creates a new asset on every import, so nothing links an element to its source and re-importing duplicates.
- **Scripts bypass everything.** `python_run` spawns an unsandboxed process with no queue (only pip installs are serialised); `written` is a project-wide before/after diff, so two overlapping runs misattribute each other's files, and `hai_3dm.save` overwrites any path. `rhino_run_python` carries neither agent nor title to the plugin, which cannot run Python yet and has not run in a real Rhino. The mirror skips curves, hidden objects and blocks.
- **Tokens are per process.** An agent's token lives until its process restarts; it is not tied to a task. The agent-to-active-task map is private to `Team`.
- **Every task ends through `finish()`**, and every turn through the hub's `finally` -> `hooks.ended`, including crash and stop. A queued task cancelled never opens a turn and passes only through `finish`.

Prior art that shaped the decisions: Revit worksharing (exclusive worksets or per-element borrowing, with display modes that show owners); Rhino Worksession (file-level locks, referenced geometry read-only); Onshape (immutable microversions, features addressed by internal id, undo as an inverse applied on top, "merge conflicts should never happen" by construction); Kleppmann on locks (a lease alone is unsafe, the protected resource must check a token); Cognition on parallel writers (they make conflicting implicit decisions; what works is shared context, single-threaded writes or independent review); Anthropic's research system (parallelism pays for breadth-first work with disjoint subtasks, and each subtask needs an explicit objective and boundaries).

## Goals / Non-Goals

**Goals:**
- Writers with disjoint scopes work at the same time; anything not provably disjoint queues, so the worst case is today's behaviour.
- The bridge, the one authority, enforces claims at the one place every scene change passes, so a model that ignores its instructions still cannot overwrite another agent's work.
- The user always sees who owns what, and each agent's work is one undo step.
- Scripts are bounded as far as they can be: reserved outputs, stamped objects, an honest after-the-fact report.
- Claim checks stay under 5 ms (p90, 100 elements in a 5000-element model) and a claim shows in the UI within 200 ms of being granted.

**Non-Goals:**
- Sandboxing Python or preventing a Rhino script from stepping outside its claim; this design detects and reports.
- Merging concurrent edits to one element, sub-element ids (faces, edges), per-agent selection, several generated panels at once, human-to-human locking, remote agents.
- Fixing the objects lost when a file with over 1000 objects is grouped per layer on import (they stay one element; `hai.source` is not set for them).

## Decisions

**Claim first, edit second: scopes are planned, not discovered.** A task carries a `scope` of up to three kinds: element `ids`, a `part` (the value of `hai.part`), and a `region` (a box in mm, matching an element when its bounds are inside or the element is created inside it). Mochi writes the scopes when it delegates, because Mochi already sees the whole request and the roster. A task with no scope claims everything, which is exactly today's exclusive writer, so old projects, user-edited agents and hand-typed requests keep working. Rejected: optimistic concurrency with base revisions (conflicts show up after the model has spent tokens, and it does nothing for the "conflicting implicit decisions" failure); Revit-style auto-borrow on first edit alone (an agent's plan is long and invisible to the others until it writes; borrowing stays as `request_claim`, the fallback); CRDT or branch-and-merge scenes (geometry has no meaningful automatic merge, and there is already one authority).

**The claim table lives in the bridge, in memory, tied to the task.** It maps task id to scope and agent, and answers three questions: does scope A overlap scope B (ids against ids, part names, region boxes by intersection, ids resolved to their element bounds when tested against a region), is element E inside task T's claim, and who holds E. Overlap tests treat an unknown element as unclaimed and a task without scope as everything. It is not saved: claims are for the life of a task. Rejected: leases with expiry and heartbeats (the holder and the checker are one process and the task has a lifecycle; a timeout would only invent a way to lose a claim mid-task); persisting claims (a restarted bridge has no running tasks).

**Fencing is by checking in the store, per call.** Kleppmann's point is that the resource must refuse a stale holder. Every scene change goes through one function in the store with the caller's agent name; it resolves the agent's current task from `Team` (agent to active task, exposed through a small interface so the scene hub does not import the team) and checks the batch against that task's claim and everyone else's. A call with no active task (after the task ended, a digest turn, a panel-close note) has no claim and is refused for scoped changes, so a late call from a stopped agent cannot write. Scene tools are pre-approved, so refusals come back as tool errors, not approval cards. The user's own edits skip the check: the user can change anything, the change is allowed, and `get_elements` notes `changedByUser` on elements the task claimed. Rejected: blocking user edits during agent work (the earlier `add-agent-turn-review` decision and the point of the tool is that a person is in charge).

**Whole-batch refusal with a message the model can act on.** A refusal names the element, the holder (agent and task title) and the options: ask for more scope, leave it, or tell the user. The existing atomic-batch rule is kept, so a half-applied plan never exists.

**Scheduler: overlap, not a flag.** `schedule()` keeps the three-at-a-time limit, one task per agent and reader-alongside rules, and replaces "any writer active" with "any active writer's claim overlaps this task's claim". With the feature off the old rule applies. A queued task records `waitingFor` (the task whose claim blocks it) so the UI can say why. Release is in `finish()` (every task ends there), plus project switch and `stopAll`; the claim is dropped before `schedule()` runs so the next task starts in the same pass. The hub's `ended` hook still closes the agent's undo group on every path.

**Per-agent undo groups and authors.** `SceneStore` keeps a map of open groups keyed by agent instead of one slot. `applyInGroup(ops, agent)` joins that agent's group and commits with its label; without an agent or group it is an ordinary transaction. Disjoint claims make groups commute: undoing one agent's step never touches another agent's elements, so the existing LIFO history stays correct and needs no per-agent stacks. A user undo while groups are open flushes each open group to history in order of last activity, reopens each empty with the same label, and undoes the newest step; this extends the single-group behaviour already tested. `scene.patch` gains `by` (`"user"` or an agent name) and `SceneState.lastChange` keeps it. The known weak spot is unchanged: an undo restores old values over a user's later edit to the same element; the claim refusal in the other direction means agents cannot create that situation between themselves.

**Tags on elements, the same convention as Rhino.** `Element` gets an optional `tags` record (name up to 64, value up to 200, at most 20), the same limits as `RhinoObject.tags`, so one UI and one query path serve both. `hai.owner`, `hai.part` and `hai.source` are reserved and set by the system. An agent sets only its own tags through `set_tags`; a reserved name is refused, so an agent cannot reassign an owner. The field is optional, files without it load unchanged, and the first save after a change writes it. Older bridges reject files that use it (strict schema): recorded as the breaking part. Rejected: a separate ownership table beside the scene (two sources of truth to save, undo and migrate); `properties` (typed values and meaning differ, and `properties` is shown and edited as design data).

**Ids: bridge makes them, agents may choose, collisions explain themselves.** The create tool keeps `type-<8 hex>` and honours an agent's id, but refuses a duplicate with the owner's name, which is what an agent needs to pick another. The importer records `hai.source` (file name and the object's Rhino id) on each element so elements can be matched to Rhino objects and a re-import can be recognised (replace-by-source is a follow-up, not in this change). Parts are tag values, not a new entity: a part is exactly the set of elements with that `hai.part`, so there is nothing to keep in step.

**The shared brief is the answer to conflicting implicit decisions.** Disjoint scopes stop overwrites but not a dome in one style on a hall in another. Mochi sets a short brief with the hand-offs (datum, grid, key dimensions, colours); the bridge puts it at the start of each specialist task and serves it from `get_claims`. Reviewer, who only reads, remains the independent check Cognition describes, and Mochi's digest turn already reports the batch.

**Python: reserve what it writes, report what it did.** `python_run` takes `outputs`, the `.3dm` files it will write. They are reserved per task (a second task naming one is refused with the holder), the offered files are the declared ones that changed, and an undeclared `.3dm` that changed during the run is reported as written outside the declaration. Kept scripts get a counter or short id in the name so same-second runs never collide. Runs may overlap; the venv and install queue are already safe for that. Rejected: serialising all Python runs (analysis runs are slow and read-only, and serialising them removes the parallelism this change exists for); running each script in its own folder (scripts read project files and the helper's relative paths would break).

**Rhino: one run at a time, stamped and diffed.** Rhino's scripting is on one UI thread, so agents plan in parallel but their scripts take turns; the bridge queues `rhino.python.run` itself instead of relying on the plugin. The message gains `agent`, `title` and the claim; the plugin, between the start and end of the undo record, stamps every object added with `hai.owner` and `hai.part` and snapshots all objects (not only the drawn ones) before and after, and returns `changes` (added, changed, deleted ids with owner tags) in `RhinoPythonResult`. The bridge compares them with the claim and reports to the agent and the user, with a one-click undo of the run. Because it cannot prevent anything it says "checked after the run" in the result. Until the plugin can run Python and has run in a real Rhino, the bridge half is tested with the fake Rhino client and the plugin half is marked as needing Rhino 8. Rejected: refusing a Rhino run that "looks" out of scope by reading its code (undecidable; false comfort); Rhino Worksession (needs the model split into files by hand and gives file-level locks, the opposite of part-level sharing).

**Display: the agent's own colour, the same everywhere.** Agent colours already exist (`TeamMemberInfo.color`). The viewer receives a map of element id to owner colour (derived from the `hai.owner` tag and the roster), draws it as an edge outline plus a light tint under selection, hover and the pending-deletion mark (the existing priority stays), draws region claims as translucent boxes, and the mirror layer does the same from its tags. The Parts list sits in the agent panel beside the team strip, fed by a claims snapshot that rides on `team.snapshot` (claims are tasks' business, and the snapshot is already published on every change). Hover in the list sets a highlight set in the viewer, separate from selection. Rejected: floating labels over elements (the viewer imports no HTML overlay today and a model with hundreds of elements would be unreadable); owner shown only as a selection-time tooltip (Revit's worksharing display modes exist because the whole-model view is the point).

**A feature switch with a safe default behaviour.** `parallelModelling` joins the features list. Off: the old scheduler rule and no owner display. A second setting, Show owners, turns off only the drawing. Tags and stamping stay on in both cases because they are data.

**Latency budgets.** Claim check: under 5 ms p90 for 100 elements in a 5000-element model, measured in a bridge unit test with `performance.now()`. Claim to screen: from the claim being granted (`team.snapshot` sent) to the box drawn, under 200 ms p90, measured by an e2e test with the fake CLI. The owner display after a change: under 200 ms from the patch reaching the viewer, measured the same way. Parallel speed-up is shown, not budgeted: an e2e test asserts the three scoped fake tasks overlap in time.

## Risks / Trade-offs

- [Mochi splits badly or overlaps scopes] -> Overlap only queues, never corrupts; the prompt and delegate description say how to split and Mochi is told when scopes overlap. A bad split costs time, not data.
- [A model ignores the brief anyway] -> Reviewer and Mochi's report remain; the brief makes the shared decisions explicit rather than guaranteeing them. Noted as the main quality risk of parallel writers, as Cognition's results say.
- [Region claims are blunt] -> A region that is too large just blocks more; `request_claim` and giving scope back let an agent right-size mid-task. Elements are matched by bounds, so a long wall crossing two regions belongs to whoever claimed it first.
- [Unsandboxed scripts] -> Detection only. The Rhino undo step and the reported list give the user the way back; the result and docs say plainly that prevention is not claimed.
- [Plugin half unverifiable here] -> Everything the bridge decides is tested with the fake Rhino client; the plugin tasks stay unchecked until run on Rhino 8 and the Python runner exists.
- [Strict schema migration] -> Optional field, loads old files; older bridges reject new ones. Recorded, and the project file `version` stays 1 because the field is additive.
- [Undo restoring over a user's later edit] -> Unchanged and documented; claims prevent the agent-to-agent version of it.
- [Cost] -> Parallel agents multiply token use (Anthropic reports about 15 times for multi-agent research); the maximum of three at once stays, and the feature is switchable.
