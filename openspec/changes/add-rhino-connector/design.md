# Design

## Context

Facts checked on 2026-10-19, and revised on 2026-10-22:
- RhinoCommon 8.35 on NuGet targets `net48` and `net7.0`; the .NET 9 SDK is installed on the maintainer's machine.
- Rhino 8 scripts in Python 3 with all of RhinoCommon and `rhinoscriptsyntax`, and installs packages from PyPI for a script that names them in `# r: package` comment lines. The agent session already loads the user's own MCP servers (`add-claude-agent-bridge`); a Rhino MCP server the user connected is simply one of them and is not part of this design.
- **Not yet checked, and the first Python task is a spike for it:** which API lets a plugin run Python 3 in process, capture its output and errors, cancel it and honour `# r:` lines (candidates: Rhino 8's `Rhino.Runtime.Code` scripting API, or writing a temporary script and running it through Rhino's Python command). Nothing below depends on which one wins, only on the plugin being able to do those four things.
- RhinoCommon meshes any Brep, extrusion, surface or SubD (`Mesh.CreateFromBrep` with `MeshingParameters`) and raises document events for added, replaced, deleted and modified objects and for selection changes. HAI's mesh asset format (`packages/scene/src/mesh-asset.ts`) and asset store (`/assets`, token required) already carry binary triangle data from the browser to the bridge; the plugin holds the session token like any local client.
- `rhino3dm` (openNURBS for Python) reads and writes `.3dm` files without Rhino. `ladybug-core` is pure Python and runs in both environments; `ladybug-rhino` needs Rhino.

## Goals / Non-Goals

**Goals:**
- What changes in Rhino shows in HAI's viewer fast: p90 under 300 ms from the change to the drawn frame for edits of up to 50 objects on the reference laptop, and a large model arrives progressively. Hand navigation stays the built-in viewer's own and is never slower for the mirror.
- The agent's capabilities are Python's: any approved library (Ladybug, NumPy, Shapely, IfcOpenShell, Pandas, ...), on `.3dm` files directly or in the live Rhino, with the user shown the code and the packages first. Rhino is the modelling and drafting host, and nothing in the workbench needs it.
- What the agent runs stays readable and reusable by the human.
- The plugin stays small: a mesh mirror, selection, and a Python runner.

**Non-Goals:**
- Sandboxing Python. Scripts can do anything the user can; the approval card is the control, as it is for a shell command.
- Wrapping, detecting or depending on any Rhino MCP server.
- Driving Rhino's own viewport or drawing feedback inside Rhino (a camera relay, a display conduit with a cursor ring). The user looks at HAI's viewer; Rhino's window is optional.
- Drawing Rhino curves, points and annotations in HAI: they are counted and listed in the HUD, not drawn.

## Decisions

**Plugin connects out to the bridge** as a WebSocket client (`System.Net.WebSockets.ClientWebSocket`, present in both `net48` and `net7.0`), rather than Rhino hosting a server. The bridge stays the single hub with one security model, and Rhino needs no open port. Rejected: Rhino-hosted server (a second listener to secure); a TCP socket server in Rhino as community Rhino MCP servers use (a different purpose, unauthenticated).

**Discovery without copy-paste.** The bridge also writes `{port, token}` to `%LOCALAPPDATA%\HAI\bridge.json` with a user-only ACL and deletes it on shutdown. `HaiConnect` reads it. Connections without an Origin are accepted only with the token and `hello.client = "rhino"`. Browsers always send an Origin, so web pages cannot use this path.

**Threading.** WebSocket receive runs on a background task. Every document change is marshalled with `RhinoApp.InvokeOnUiThread`. Meshing is done in slices of at most 10 ms so Rhino's interface stays usable while a large model is mirrored. A Python run changes the document, so it runs on the UI thread and blocks Rhino's interface while it runs; that is why every run has a time limit.


**The mirror.** The plugin subscribes to `RhinoDoc.AddRhinoObject`, `ReplaceRhinoObject`, `DeleteRhinoObject`, `UndeleteRhinoObject` and `ModifyObjectAttributes` (layer, colour, name, visibility), collects them for 100 ms and sends one batch: for each added or changed object a descriptor `{ id, name, type, layer, color, bounds, asset, changedAt }`, for each deleted object its id. The mesh of an object is made with RhinoCommon (a fast render mesh, with a cap on triangles per object) in millimetres, Z up, written in HAI's mesh asset format and uploaded as one asset per object through the bridge's asset store with the session token, before the descriptor that names it is sent. The bridge keeps a table of descriptors by Rhino id (and so can greet a page that connects later), relays batches to the web app, and clears the table when Rhino disconnects. The web app fetches assets as they are first needed (`ModelAssets`) and draws the table as a read-only layer: it is not in the `SceneDocument`, so it is not saved with the project, not in the undo history and not editable by `update_elements`. The first sync of a document sends objects in order of size, small first, and the HUD shows `n of m`. Rejected: driving Rhino's viewport and showing Rhino's window (the user would look at Rhino, not HAI, and the plugin needs a camera relay and a conduit); streaming Rhino's viewport as images (bandwidth, no picking, and a second camera); putting Rhino objects into the HAI scene as `imported` elements (they would be saved, undoable and editable by two owners).

**Latency.** Each descriptor carries `changedAt` (epoch ms, from the plugin's clock when the batch is sent). After the web app draws the frame that includes the change it computes `drawnAt - changedAt`, both wall-clock on the same machine, and shows the p90 over the last 3 s as **Rhino to HAI** in the HUD. The budget is 300 ms p90 for edits of up to 50 objects; the bridge test with a fake Rhino client checks the relay and the web draw against it, and the demo records the real figure.

**Picking and the pointer.** The hand pointer works in HAI's viewer as it does today. The viewer maps a pick on a mirrored mesh to its Rhino id; a pinch tap sends `rhino.select { ids }` and the plugin selects those objects after `UnselectAll` (a tap on empty space clears). The object under the pointer is the `pointed` Rhino object in the user context.

**Selection sync.** Subscribe to `RhinoDoc.SelectObjects`, `DeselectObjects` and `DeselectAllObjects`; debounce 50 ms; send ids with object type and layer full path. The web app highlights the selected mirrored objects, so a selection made with the mouse in Rhino shows in HAI.

**The mode decides what the agent has.** There is no host to switch: the user always looks at HAI's viewer. Settings > Modelling (Automatic, Rhino, Python only) decides whether the agent has Rhino's tools, and the mirror layer is shown while Rhino is connected and the mode is not Python only. When Rhino disconnects the bridge clears the table and the layer disappears.

**The agent can move the camera.** A `set_view` tool (azimuth, elevation, distance, a target point, or element ids to frame) is relayed to the viewer like `view.capture` and animates the view over 400 ms. It does not change the scene, so every agent has it. Rhino geometry is moved with `rhino_run_python` (rotate, move, mirror, array and the rest of RhinoCommon); the built-in scene elements still have no rotation field, which is outside this change.

**Python, not a list of tools.** The agent gets one general tool for the workbench (`python_run`, independent of Rhino) and one for the open Rhino document (`rhino_run_python`), plus a cheap read tool (`rhino_get_document`) so it can look before it writes. The workbench is the agent's capability layer and Rhino is a host it can draft in: that is why the workbench is its own capability (`python-tools`) and works with Rhino closed. An LLM writes good Python for Rhino, and Python is open-ended: it reaches every RhinoCommon call, loops and conditions in one round trip, and any library (Ladybug for sun and climate, NumPy for the maths) with no tool to add per capability. Rejected: a curated tool per operation as in a Rhino MCP server (every missing operation is a missing capability, and each tool is another thing to maintain); depending on a third-party Rhino MCP server (its tool list is the ceiling, and it must be installed, detected and kept in step with Rhino).

**Live run protocol.** The bridge sends `rhino.python.run { id, code, timeoutMs }`; the plugin runs it on the UI thread inside one undo record labelled `HAI: <agent>: <title>`, and answers `rhino.python.result { id, ok, stdout, result, error, durationMs }`. `result` is the value of a variable named `result` if the script set one. Output is capped at 20 000 characters and an error carries the message and the last lines of the traceback, so the agent can fix its script. The default time limit is 60 s. Stop cancels the run; if the Rhino scripting engine cannot interrupt it, the plugin abandons the result at the time limit and the HUD says Rhino is still busy (the spike measures which). The tool chip shows the round-trip time; the budget for the overhead of a trivial script is 500 ms, measured by the bridge from request to result.

**Packages are part of the approval.** The bridge reads the `# r:` lines out of the script before it runs and puts the package names on the approval card beside the code, because installing from PyPI runs someone else's code. Always allow remembers the tool for the project and the packages the user has already approved; a run that adds a package asks again. Rejected: allowing any package once the tool is allowed (the one approval a user gives for "run Python" should not silently stretch to new third-party code).

**A managed Python environment, the workbench.** `python_run` runs in a virtual environment HAI creates in `.hai/python` (git-ignored) from a Python 3.10+ it finds on the machine (the `py` launcher, then `python`). The first use shows an approval card listing what it will install (`rhino3dm`, `ladybug-core`, `numpy`); a run asks for any further library through an explicit `packages` argument that the card also lists, so the agent is never limited to a list HAI chose. Libraries are installed on the user's machine from PyPI at the user's approval and are never bundled or shipped, so their licences are the user's to accept, not part of HAI's (the project rule against GPL and AGPL in shipped code stands). The working directory is the project folder; output and the time limit work as in live mode; Stop ends the process. Rejected: the user's global Python (HAI would change it); a bundled Python (size, licensing and updates for a feature most runs of the live mode do not need); `Rhino.Compute` (a licence and a hosted service for what `rhino3dm` does locally).

**Runs are kept as scripts.** Every run, in either place, is written to `.hai/scripts/<timestamp>-<title>.py` with its packages, output, result and outcome in a header comment, so the human can open, edit and rerun it (a rerun is a request through the same approval) and the agent can find and extend earlier work. The folder is git-ignored with the rest of `.hai`. Rejected: keeping runs only in the chat history (not reusable by the human and lost with the session).

**Files come back through the importer.** When a `python_run` leaves a new or changed `.3dm` in the project folder, the bridge tells the web app, and the HUD offers **Import into viewer** (the existing 3dm import, `add-precision-aids-and-3dm-import`) and, when Rhino is connected, **Open in Rhino**. Nothing is imported or opened without that click.

**Two modelling modes, chosen in Settings.** Settings > Modelling has three choices: **Automatic** (the default: Rhino when it is connected, otherwise the Python workbench), **Rhino** and **Python only**. The bridge works out the mode in use and tells the agent in the descriptions of its tools, so it plans for what it has: in Python only mode `rhino_run_python` and `rhino_get_document` are not offered, and with Rhino the agent is told the workbench is for analysis and files. The choice is a user setting kept in `.hai/settings.json` like the others, so it follows the workspace between a machine with Rhino and one without. Rejected: a mode picked by the agent (the user knows which machine this is, and a run that expects Rhino on a machine without it fails late).

**What the workbench can model.** `docs/decisions.md` (2026-10-23) has the measurements. `rhino3dm` builds NURBS curves and surfaces, Breps from surfaces, revolves, extrusions, ruled surfaces, planar trimmed shapes and meshes, with layers and names, and writes and reads `.3dm`. It has no loft, sweep, boolean, fillet, offset, intersection or Brep meshing, and cannot build a trimmed Brep from parts. The `python_run` description states this, so the agent chooses another way (build the surface from control points, or ask to use Rhino) instead of calling something that is not there.

**A helper so what Python writes can be seen.** HAI's importer draws only the render meshes a file stores, and `rhino3dm` stores none. So the workbench offers a small module (`hai_3dm`, in this repository under `apps/bridge/python`, found through `PYTHONPATH` so it is never copied into or versioned with the environment; the desktop package copies the folder) with `save(model, path)`: it attaches a render mesh to every Brep face and extrusion (surface evaluated on a grid; a planar trimmed face is triangulated from its outer loop so a disc is not drawn as a square) and then writes the file. The runner that starts every script (`hai_run.py`) ends the process with `os._exit` after writing its outcome, because `rhino3dm` crashes at interpreter exit once `SetMesh` has been used. The agent is told to save through it. Rejected: leaving it to the agent (every script would repeat, and often get wrong, the meshing and the exit); trimmed free-form faces are not meshed in this change and are reported as skipped.

**Tools by role.** `rhino_run_python` changes the model, so it goes to the agents marked as changing it (Architect, Product). `python_run` can only write files, so Climate gets it too (Ladybug and other analysis libraries). `rhino_get_document` is read-only and goes to everyone, Reviewer included. `set_view` changes only the camera, so every agent has it. The bridge offers an agent only the tools its definition lists (`add-mochi-agent-team`).

**Status.** The plugin reports `python: ready | unavailable` in its hello and after any change, with a reason. The bridge reports the managed environment as `missing | ready | unavailable` with a reason (no Python found, install failed). The HUD shows both and says how to fix each.

**Build and test.** `plugins/rhino/HAI.Rhino.csproj` (SDK-style, `net48;net7.0`, RhinoCommon `8.*` as a compile-time-only reference). Message parsing, `# r:` line parsing, result shaping, the change coalescer and the mesh asset writer sit in a plain `HAI.Rhino.Core` library with xUnit tests that run in CI without Rhino. Meshing itself needs Rhino and is checked by a manual script in `demos/`. The bridge side is tested against a fake Rhino client that uploads mesh assets, sends batches and answers Python runs, and the file mode against a real managed environment (skipped where no Python is installed).

## Risks / Trade-offs

- [A virtual environment under a long project path fails to install on Windows (260 characters)] → The environment's location is checked before it is created; if the path is too long it is made under `%LOCALAPPDATA%\HAI\python\<project hash>` instead and the HUD says where. Found in the spike.
- [Windows Application Control blocks an unsigned binary wheel] → The install error is returned to the agent and the HUD with the blocked file named, and the agent is told to use the packages that are already installed. HAI never installs a package without the user's approval card.
- [Trimmed free-form faces cannot be drawn from a Python-written file] → Reported as skipped on import with the reason; planar trimmed faces, revolves and untrimmed surfaces draw. Rhino mode has no such limit.

- [A large Rhino model is slow to mirror, or too heavy for the browser] → Progressive first sync (small objects first) with a count in the HUD, a cap on triangles per object, batches coalesced at 100 ms, and an object over the cap is drawn as its bounding box with a note; the HUD shows the measured p90.
- [The C# mesh writer and the TypeScript reader drift apart] → A contract test: C# writes a fixture, TypeScript loads it, and the other way round for the bounds.
- [Curves, points and annotations are not drawn] → They are counted in the HUD ("12 curves not drawn") so a missing object is explained.
- [The plugin cannot be tested in CI without Rhino] → Pure core library with unit tests; integration covered by a fake Rhino client in bridge tests plus the manual demo script.
- [A long script freezes Rhino's interface] → A 60 s default limit, Stop, and the HUD says Rhino is busy; the agent's instructions tell it to keep runs short and to split big jobs.
- [Python can do anything, including harm] → Nothing runs without the user seeing the code and the packages; no sandbox is claimed, and `docs/rhino.md` says so plainly.
- [A package that Rhino or the managed environment cannot install] → The error comes back to the agent and the HUD; the script can fall back to what is installed.
- [Python gets cancelled but Rhino cannot interrupt it] → The spike measures it; the result is abandoned at the limit and the HUD says Rhino is still busy.
