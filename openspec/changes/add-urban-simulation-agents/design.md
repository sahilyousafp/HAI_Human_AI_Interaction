# Design

## Context

What exists (read in the code and in the docs):

- The roster is data: `DEFAULT_AGENTS` in `apps/bridge/src/agent/roster.ts` (description, tools, model, prompt, `meta` with aliases, colour, `writes`, `lead`). `ensureDefaultAgents` writes only the definition files that are missing, so existing projects gain new default agents and keep edits. Colours, aliases and speech addressing are read from data in the web app; only the Agents form's capability list (`AgentsView.tsx`) and a few tests and docs name agents.
- Tools reach an agent in two filters: `allowedHaiTools` (roster) decides which `HAI_TOOLS` groups an agent gets, and the tool server removes every tool not in the caller's list (`scene-tools.ts`, end of `createSceneMcpServer`). A non-writer loses the panel group in `allowedHaiTools`; the panel broker itself has no role check.
- `mcp__hai__*` tools are pre-approved (`approvals.ts`); anything else asks. Features behind a switch are registered only while it is on (`generatedPanels`, `server.ts`).
- The bridge makes no outbound request. README, `docs/desktop.md` and `SECURITY.md` promise that nothing leaves the machine except Claude Code itself, and panels run under `connect-src 'none'`.
- The project has no georeference. `sun_study` takes latitude and longitude as arguments. Model units are millimetres, +Y is north.
- The Rhino connector already draws a read-only mirror of Rhino objects outside the project document (`MirrorLayer.tsx`, meshes from the asset store); agents' own cameras already tag user-only objects (`userData.userOnly`, `cleanColor`) and see everything else.
- Extensions install an MCP server into the project (`claude mcp add --scope project`), and an agent uses it by listing `mcp__<server>__<tool>` in its definition's tools. Those calls ask for approval. The Python workbench already installs `ladybug-core` on approval.

## Goals / Non-Goals

**Goals:** agents can learn about the place around a project from open data and say how old it is; the user stays in control of what leaves the machine; the city around the model is visible to the user and the agents without becoming part of the model; every agent can show information in a panel without gaining a way to change the model.

**Non-Goals:** a GIS; keeping a city database; accounts or keys; live (sub-minute) satellite data; certified simulation results; changing how writers claim parts or how workers work.

## Decisions

**Open data is HAI's own typed tools in the bridge, behind one switch.** The bridge fetches, not the browser and not the agent's `WebFetch`: one place can enforce the host list, the size and time limits, the cache and the record, and the app can say exactly what leaves. Tools are registered only while Open data is on (the pattern of `generatedPanels`), so an agent's tool list is the proof of what it may do. They are `mcp__hai__*` and so pre-approved; the consent is the switch plus the per-source list the user saw (see the tool-approval delta). A request is built by the adapter from a place, an area, a time or a search text, so nothing from the project can be in it by construction: adapters take typed arguments, not free URLs, except the portal tools, which take a portal host from the allowed list. Rejected: giving agents `WebFetch`/`WebSearch` for data (untyped, no cache, no licence tracking, one "always allow" opens the web); one external MCP server per source (many installs, uneven quality, no common record); fetching in the page (CORS, and the page is the wrong place for a record of egress).

**A guarded fetch is the only way out.** One module (`open-data/fetch.ts`) owns every request: HTTPS only; the host must be an adapter's host or a portal host from the starter list or the user's list; the address is resolved first and refused when it is loopback, private or link-local (including after every redirect, at most 3, each re-checked); 10 s timeout; response size cap per kind (2 MB JSON, 20 MB raster window); content types allowed per adapter; an identifying User-Agent `HAI/<version> (open source; <project url>)`; per-host rate limit with the hosts' own published etiquette (for Overpass, one request at a time and a 30 s pause after a 429). Adapters call nothing else. Rejected: trusting the agent's URL after a host-name check only (DNS rebinding and redirects bypass it).

**Cache on disk, keyed by the request.** `.hai/open-data/<adapter>/<hash>.json` (or the raster window) with a lifetime by kind: weather 10 minutes, forecast 1 hour, normals 30 days, buildings 7 days, vegetation 30 days, surface temperature 24 hours, portal catalogues 1 day. The cache returns the original `fetchedAt` and `observedAt`, so the age an agent reports is honest. The cache is part of the workspace, not the project, and is cleared from Settings.

**Every result is an envelope.** `{source, licence, attribution, observedAt, fetchedAt, ageMinutes, cached, inferred?, data}`; a building height from levels is `inferred: "levels x 3 m"`. The instructions of the three data agents and the tool descriptions say to repeat source and age. A shared attribution list in Settings shows the sources used in the session.

**Sources: one adapter each, all keyless; terms re-checked when the adapter is written.** What was checked in this design (web, 2026-10):

| Use | Source | Terms and access | Notes |
|---|---|---|---|
| Weather now and forecast | MET Norway Locationforecast 2.0 | free, no key, an identifying User-Agent is mandatory (403 without), rate limits, data under open licences (CC BY 4.0 / NLOD; text of the terms to be read when implementing) | global default |
| Weather, US | NWS `api.weather.gov` | US government data, no key, User-Agent required | selected for sites in the US |
| Weather alternative | Open-Meteo | data CC BY 4.0; the free API is for non-commercial use under 10,000 calls a day; commercial use needs a key | off until the user acknowledges the limit |
| Normals, solar | NASA POWER (MERRA-2, CERES) | free, reported as keyless by third parties; the official terms are to be confirmed | monthly and climatology endpoints, 20 parameters a call |
| Buildings | OpenStreetMap through the public Overpass API | ODbL, attribution "OpenStreetMap contributors"; the public instance asks for little and polite use, caching, identification, a 30 s pause after 429 | heights from `height`, else `building:levels` x 3 m, flagged as inferred |
| Vegetation cover | ESA WorldCover 10 m (2021) | CC BY 4.0, Cloud Optimized GeoTIFF in the public bucket `esa-worldcover`, no account | class 10 is tree cover; windowed reads |
| Greenness | Sentinel-2 L2A through the Earth Search STAC | open data on AWS, COGs, no account | latest cloud-free scene for NDVI |
| Surface temperature | Landsat Collection 2 Level 2 (surface temperature band) through the Planetary Computer STAC | catalogue lists public domain; keyless reading with a token the service hands out without an account | 100 m, revisit 8 to 16 days: a scene, not live data |
| Portals | CKAN action API, Socrata SODA, ArcGIS Hub | per portal; each dataset's own licence is reported | host list shipped and user-extended |

Rejected: NASA ECOSTRESS (needs an Earthdata login, which is a credential the app would have to hold), Google Earth Engine and Google Open Buildings (account), commercial weather APIs (key and payment), Overture and 3D BAG now (good, but one adapter each, so a follow-up behind the same seam), GOES-R hourly surface temperature (netCDF4 in Node is a poor fit; a follow-up through the Python workbench).

**"Real time" is honest.** Weather is minutes old, a satellite ground-temperature scene is days old. Nothing is called live that is not, tool descriptions say how old each kind can be, and the Simulation agent's instructions require it to say that a scene is a moment in the past. A "latest scene" query takes a `maxAgeDays` argument; an older scene is not returned silently.

**The site is a small saved record.** `site: {lat, lon, northDeg, anchorMm: [x, y]}` beside the project's settings, saved with the project file, validated by `@hai/protocol`. Conversion between geographic coordinates and model millimetres is a pure function in `@hai/scene` (a local tangent plane around the site, accurate to centimetres within 2 km, then the north rotation). It is set in Settings or through a `site_set` tool whose call always shows an approval card (it is not pre-approved: it saves something and decides what places later requests are about). Rejected: guessing the site from the browser's geolocation (a privacy prompt and wrong for most projects), a geographic CRS in the scene document (a migration with no use yet).

**The context layer is the Rhino mirror pattern.** A bridge `ContextStore` holds the items (building prisms, tree points, raster overlays with their legend) with source and date, persists them beside the project (`.hai/context/`), and sends them to the page as `context.set` / `context.clear` messages; meshes use the existing asset store and `MeshPart` format, so there is nothing new on the wire for geometry. The page draws them in a `ContextLayer` modelled on `MirrorLayer`: no pointer events, not in the pick list or snapping, neutral tint, no hover or selection. It is not tagged `userOnly`, so agents' own cameras and the sun-study render show it (and its shadows are real); `Show context` hides it for the user only, by a flag the shot step does not honour. A layer built for an older site gets an out-of-date mark and is replaced only by a new fetch. Adoption is a writer tool (`context_adopt`) that creates ordinary elements through the same claim-checked create path as any edit, tagged `hai.source`, in the agent's undo group. Rejected: importing context as elements (a city block is thousands of elements in the undo history and the saved file); a separate scene (a second renderer path and no shadows on the model).

**Panels for all agents: information only when the agent cannot change the model.** `allowedHaiTools` stops stripping the panel group, and the lead gets it too. `PanelDocument` gets an optional `readOnly`, set by the bridge (never trusted from the agent) for every panel opened by an agent whose roster entry does not write. The page's panel client refuses `preview` and `commit` from a read-only panel (see Resolved while applying), tells the panel's script, tells the bridge, and shows Close instead of Done; the bridge tells the agent when the panel closes. The refusal is in code, not in the prompt, as for every other writer rule. `offer_panel`/`open_panel` descriptions and the roster text say what an information panel is good for. The panel broker is unchanged: one open panel, a queue of two, the agent named on it. Helper subagents are not given panel tools (they run under their parent's token and would pass its role). The instructions text changes, so `instructionsVersion` changes and old conversations start fresh, as the docs already say happens.

**`info-panels` supersedes a pending requirement.** `add-generated-panels` (not yet archived) has the requirement "Only agents that change the model can offer panels". This change states the new rule as its own capability so the two deltas do not collide. When `add-generated-panels` is archived first, its requirement is replaced by a MODIFIED delta of `generated-panel` with the text of `info-panels` (a task of this change). Rejected: editing the other change's artifacts now (it is a finished change with its own history).

**Ladybug Tools is a user-installed extension, with a licence boundary.** HAI is Apache-2.0 and its rules forbid GPL, AGPL and non-commercial dependencies in shipped code. The Ladybug Tools MCP server (community project, GPL-3.0, experimental, stdio only, Python 3.12 through uv, a large first download, Windows its main platform) is therefore never a dependency, never vendored, never started by the app on its own. It is a curated entry in the Extensions tab that shows the licence and the command before it does anything, and when the user confirms, the existing install flow adds it to the project like any extension. The simulation agent lists `mcp__ladybug__*` among its tools; HAI speaks MCP to it, as it would to any server. Calls ask for approval (they are not `mcp__hai__*`). The same separation holds for the Python workbench's `ladybug-core`, which is installed on approval into the user's environment. Rejected: our own wrapper tools around the Ladybug libraries in the workbench (we would maintain a thin product on GPL code that moves quickly, and the licence boundary is blurrier); skipping Ladybug (the user asked for it).

**Ladybug has its own model; ours reaches it as a description.** The server builds its own Honeybee model in its own "Garden". The first task is a spike with a real install to learn which of its tools take geometry and in what form. Whatever the spike finds, the HAI side is `simulation_geometry`: the model (and optionally the context layer as shading) as a simplified, metre-based, +Z-up description (footprints with heights, levels, openings where the model has them) plus a list of what was simplified, which the agent turns into Ladybug calls. If the spike shows the server can import a file, a later change can add an export; this one does not promise it. Rejected: exporting HBJSON ourselves (needs the Honeybee schema, which is the GPL/AGPL library's contract, in our code).

**Roles.** Urban, Simulation and Climate are readers (`writes: false`): they keep the single-writer rule intact, never need claims, and can run alongside the writers. Adoption goes through writers. Each gets a distinct colour (checked in both themes), aliases for speech, and a read-only helper entry (the helper for each teammate is generated from the roster). The Agents form gets capability rows for open data and context.

**Mochi hands out the work.** Mochi's instructions gain one line each: site, buildings, vegetation, portals go to Urban; weather and climate to Climate; surface temperature and simulations to Simulation. Mochi may also answer a request to show information with a panel of its own.

**Budgets (measured at apply).** Cached tool answer under 50 ms; an uncached weather or portal answer under 3 s p90 on a normal connection; 500 buildings fetched and drawn in the layer under 5 s; the layer drawn without a gap longer than 50 ms between the user's own frames while 2000 building prisms are on screen (instanced); a raster window of 1 km at 10 m (10,000 cells) read and summarised under 4 s p90. Measured by the e2e speed tests with a local fake data server, and once live.

## Risks / Trade-offs

- [Overpass and the other free servers are slow, rate-limited or down] -> cache, a polite per-host limit, typed errors the agent can report, a radius limit (1 km default, 2 km maximum) and a building cap.
- [Licence terms change or are misread] -> each adapter records its licence and attribution in its envelope; the terms are re-read when each adapter is written; a non-commercial free tier is off by default.
- [Pre-approved fetch tools could be abused by a prompt-injected agent to send data out] -> requests are typed, built by adapters, contain only place and time, go only to listed hosts, and the record is visible; the portal tools take only listed hosts. A search text is the one free string, and it is the agent's own query.
- [A read-only panel is still a web page] -> the same sandbox, size and rate limits and no network; the bridge, not the frame, refuses writes.
- [Ladybug install weight and instability] -> optional, a clear message and a fallback to sun studies; the licence and experimental warnings are shown first.
- [OSM heights are patchy] -> flagged as inferred, with the share of buildings that have a height reported with the result.
- [An agent's idea of "now" differs from the data's] -> `observedAt` and `ageMinutes` come from the data; instructions require them in the report.
- [The new instructions invalidate conversations] -> accepted and documented; it is the existing behaviour when the instructions change.

## Migration

The default team gains Urban and Simulation through `ensureDefaultAgents`, which writes only missing files, so projects keep their edits. Open data is off and projects have no site until the user acts. Panels for all agents change the instructions, so saved agent conversations start fresh once. Agents started before the change do not have the new tools until restarted. Rolling back is turning Open data and Generated panels off.

## Open Questions

- Which portal hosts belong on the shipped starter list (a short list of large city portals, to be agreed when the adapters are written; the user can add their own).
- Whether the Ladybug server can import geometry from a file; the spike answers it and may add a follow-up change.
- Whether 3D BAG and Overture should be the next building adapters (they give measured heights where OSM has none).

## Resolved while applying

- **A panel's preview and commit never pass through the bridge.** They are sent by the page as the user's own scene edit, so the bridge's tool server cannot refuse them. What is trusted is the page's panel client: the sandboxed panel can speak only through the page's one port, and the client refuses `preview` and `commit` when the panel is marked read-only. The bridge decides the mark from the calling agent's role (an agent whose tools include none that change the model), sets it on `panel.open` and `panel.update`, and the agent cannot set or clear it (the `open_panel` input drops it, and `PanelDocument` stays strict). A refusal sends `panel.refused` to the bridge, which tells the agent when the panel closes.
- **The check for "changes the model" is the tool list.** `changesModel(tools)` is true for a caller with any of the write tools, or with no list (the single unnamed session, which has every tool), so a worker of Architect is a writer and a worker of Climate is not.
- **The instructions version changed** (a short panel bullet in the base instructions, so every agent knows an information panel exists), as the design said it would.
- **The site is not in the scene document, and has no undo step.** A site field in the document would need an operation kind that every consumer of operations (claims, history, the Rhino mirror, the exporters) understands. The site lives in `.hai/site.json` of the project, read again when another project opens and sent to every page as `site.snapshot`; a user's edit is `site.set`; an agent's proposal is `site_set`, which is never pre-approved (it asks every time, and its card has no "Always allow": `ApprovalRequest.once`). The spec asks for Settings to show the values and Clear to remove it instead of an undo step.
- **Role grants.** An agent's definition file is never rewritten, so an existing project's Climate has no open-data tools in its file. `AgentMeta.grants` (names of read-only `HAI_TOOLS` groups, from the defaults unless `.hai/agents.json` says otherwise) adds the groups a role has; only groups that change nothing can be granted. `grants` is not sent to pages.
- **The only way out is one client.** `OpenDataClient` owns every request: the transport is the real HTTPS one (the address is checked as the socket connects, so a name that resolves to a private address is refused at the moment of use, not before), or a stand-in in tests. Nothing else in the bridge reaches an open-data host. Tests never touch a real host.
- **The fake CLI got a generic `tool NAME JSON` script**, so any app tool can be driven end to end without a script of its own.
- **The context layer sends compact data, not meshes.** A building is a footprint, a height and where the height came from; the page extrudes all of them into one merged mesh (one draw call, 2000 buildings in about 100 ms, no dropped frame while the view is turned), and trees are one instanced mesh. The asset store and `MeshPart` format the Rhino mirror needs for arbitrary geometry would be heavier than the data. `context.snapshot` carries all items (at most 3000 buildings, 5000 trees, 4 rasters; the nearest are kept) and is sent whole on every change.
- **An adopted building is a slab.** The scene has no polygon prism element except a slab, which extrudes an outline by a thickness; a building adopted from the layer is a slab of its footprint whose thickness is its height, tagged `context.source` and `context.id` (the names under `hai.` are the system's and an agent's call may not write them).
- **The layer is not picked because it has no element id.** Picking and snapping already skip any object without one, so a ray passes through the layer to the model behind; the layer group is tagged `contextLayer`, which the agent-picture step shows even when the user hid it.
- **The sun's shadow map widens** to `1.2 x` the layer's reach from the origin (60 to 300 m) with a 4096 map past 100 m, so neighbours' shadows reach the model.
- **Rasters are read by ranges through the same guarded client.** `geotiff` (MIT) reads Cloud Optimized GeoTIFFs; its reader is given a client that sends every range through `OpenDataClient`, so the host list, the size and time limits and the record apply to each range (4 MB at most, no pacing for object stores). The window is resampled onto a grid aligned to the model's axes (whatever way north points, UTM or degrees), which gives overlays and statistics that line up with the model. Scenes are found through a STAC search; vegetation uses ESA WorldCover (2021) and the newest Sentinel-2 scene with little cloud, as the spec says "the latest cloud-free scene with its date".
- **Derived results are cached by what they were asked, not by their parts.** A raster answer is a handful of numbers and a picture, saved for its lifetime under the question (`derived`); the ranges themselves are not saved. `urban_metrics` finds a saved land cover (`peekDerived`) instead of fetching, so a metric whose data was never fetched is reported missing, as the spec requires. The layer records which "source:kind" sets were fetched, so "none there" differs from "never asked".
- **Overpass answers may be large** (8 MB, above the 2 MB for text), because a dense 2 km square is several megabytes of geometry; buildings that are relations (some large or complex ones) are not included in this version.
- **The starter list of portals** is the one shipped in `@hai/protocol` (data.gov, data.gov.uk, opendata.swiss, five city Socrata portals and ArcGIS Hub); the user can add hosts. Real portals' answers are checked in the live task (8.1); the adapters follow each platform's documented API shape.
- **Ladybug spike, static part.** Read from the project's repository and package metadata, not run: `lbt-mcp` 1.2.3 (LoftyTao) is GPL-3.0, speaks MCP over stdio, runs as `<installed Python> -I -m ladybug_tools_mcp.server` with the environment variables `LADYBUG_TOOLS_GARDENS_ROOT` and `LADYBUG_TOOLS_MCP_INSTALLATION`, and installs through `uvx --isolated --python 3.12 --prerelease allow lbt-mcp@1.2.3 install [--generate-config]`, which also prints the settings to use. Its tools are prefixed `LB_` and `GD_` and work on its own "Garden" model, so HAI's side stays `simulation_geometry` (the agent rebuilds a simplified model through those tools). The curated card in the Extensions tab carries exactly these values and fills the add-server form; nothing is installed or added until the user presses Add server. Whether the server can import a geometry file, how long the install takes and how it fails are still unknown: they need a real install on the user's machine, which this change does not start (task 6.3 stays open until they run it).
